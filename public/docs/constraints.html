⚙️ Synchronous Execution (No Event Loop)

Impact: Low Common: Rare

The Constraint

All code on the GPU executes synchronously and sequentially. There is no event loop, no scheduler, and no true asynchronous execution.

async/await syntax is parsed and compiles, but await does not actually suspend execution—it simply passes through the expression value. 

// This compiles and runs, but synchronously:
async function fetchData() {
  const result = await somePromise;  // ← await is stripped; synchronous
  return result;
}

// GPU execution:
// 1. Call somePromise (synchronously)
// 2. Immediately use result
// No suspension, no context switching

Why?

GPUs have no OS-level threading, no preemption, and no I/O subsystem. All work happens on a fixed schedule: load data, compute, store results. Adding true async would require cooperative multitasking (coroutines), which adds code size and memory overhead.

When It Matters

Almost never in HTTP servers. Typical workload:

  • ✅ Synchronous request processing (read input, compute, write output)
  • ✅ Batched parallel requests (256+ at once)
  • ❌ Awaiting I/O on GPU (network, disk) — GPU can't do I/O
  • ❌ Coordination between async tasks — use external message queue instead

✓ How to Handle It

Option 1: Synchronous APIs

// Instead of:
async function compute(x) {
  const y = await transform(x);
  return y * 2;
}

// Use:
function compute(x) {
  const y = transform(x);  // Direct call
  return y * 2;
}

Option 2: Batch Pre-processing (CPU)

// Pre-fetch all required data on CPU, pass to GPU
const results = symmetra.compute({
  input: data,
  metadata: precomputedMetadata  // Load this on CPU first
});

Option 3: Use Node.js for I/O

// Node.js (with async)     GPU (synchronous)
app.post('/compute', async (req) => {
  const data = await req.json();      // I/O on CPU
  const result = gpu.compute(data);   // Pure compute on GPU
  res.json(result);
});

💾 Static Memory Allocation

Impact: Medium Common: Sometimes

The Constraint

GPU memory is stack-based and fixed-size. Arrays must be pre-sized; you cannot dynamically grow them at runtime like in JavaScript. 

// This works — fixed size:
const arr = [1.0, 2.0, 3.0];
arr[1] = 99;

// This doesn't work as expected:
arr.push(4.0);  // ← No dynamic allocation; array stays size 3
arr.from(someIterable);  // ← Returns input as-is; no new array created

Why?

GPU kernels are compiled with a fixed memory footprint. NVIDIA CUDA allocates registers and local memory at kernel launch time. Dynamically resizing arrays would require:

  • Memory pools and fragmentation management
  • Serialization back to CPU
  • CPU-GPU round-trip (adds 100µs+ latency)

✓ How to Handle It

Option 1: Pre-size Arrays

// Know max size upfront:
const MAX_RESULTS = 256;
const results = new Array(MAX_RESULTS);
let resultCount = 0;

for (const item of items) {
  if (resultCount < MAX_RESULTS) {
    results[resultCount++] = process(item);
  }
}

Option 2: Variable-Length Data (CPU Pre-processing)

// Node.js server
app.post('/transform', async (req) => {
  const items = await req.json();

  // GPU constraint: must know size upfront
  const results = symmetra.transform({
    items,
    maxResults: 256
  });

  return res.json(results.slice(0, results.actualCount));
});

Option 3: Schema-Based Memory Layout

// Define structure upfront
const schema = {
  users: 1000,        // Max 1000 users
  requestsPerUser: 10, // Max 10 reqs/user
};

const batch = {
  userIds: new Array(schema.users),
  requests: new Array(schema.users * schema.requestsPerUser)
};

// GPU processes fixed structure
gpu.process(batch);

Best Practice

Think of GPU as a deterministic state machine, not a dynamic runtime. Allocate once at startup, fill with data per request, compute, return results.

🌍 No Unicode Support

Impact: Low Common: Rare

The Constraint

String handling is ASCII/UTF-8 bytes only. No Unicode normalization, no grapheme clusters, no case-folding. 

// ASCII/UTF-8 works:
const name = "Alice";
name.toUpperCase();  // ✓ "ALICE"

// Unicode operations don't work:
const emoji = "👍";
emoji.toUpperCase();  // ✗ No Unicode lib
emoji.normalize();    // ✗ No-op (returns input)

Why?

Full Unicode support requires the ICU (International Components for Unicode) library, which is 20+ MB and unsuitable for GPU kernels. Symmetra uses simple byte-level operations instead.

When It Matters

  • ✅ ASCII text (names, IDs, domains, tokens)
  • ✅ UTF-8 byte sequences (stored/transmitted as-is)
  • ❌ Case conversion on non-Latin scripts (Cyrillic, Arabic, etc.)
  • ❌ Grapheme-aware string slicing
  • ❌ NFKC normalization for comparison

✓ How to Handle It

Option 1: Pre-process on CPU

// Node.js (has full Unicode support)
const normalized = str.normalize('NFKC').toLowerCase();
const result = gpu.process({
  input: normalized  // Send pre-processed data
});

Option 2: Use ASCII Equivalents

// Instead of relying on Unicode case folding:
function normalize(s) {
  // Simple ASCII-only normalization
  let result = '';
  for (let i = 0; i < s.length; i++) {
    const c = s.charCodeAt(i);
    if (c >= 97 && c <= 122) result += String.fromCharCode(c - 32);  // a→A
    else result += s[i];
  }
  return result;
}

Option 3: Skip Unicode Operations on GPU

// Only do string matching, not normalization, on GPU:
const query = 'Alice';                  // Pre-normalized on CPU
const matches = gpu.findMatches({
  items,
  query,
  options: { caseSensitive: false }
});

Workaround Overhead

Pre-processing on CPU costs ~1–5µs per request. Negligible compared to GPU computation (typically 50–500µs).

🔍 Simplified Regex Engine

Impact: Low Common: Rarely

The Constraint

Symmetra uses a non-backtracking NFA (Nondeterministic Finite Automaton) for regex. This covers 95% of real-world patterns but doesn't support:

  • Backreferences (\1, \2)
  • Possessive quantifiers (++, *+)
  • Atomic groups ((?>...))
  • Lookahead/lookbehind (parsed but don't actually assert)
// These work:
/\d{3}-\d{4}/.test("123-4567")         // ✓ Simple patterns
/^[a-z]+$/.test("hello")               // ✓ Character classes
/(cat|dog)s?/.test("dogs")             // ✓ Alternation + quantifiers
/(?:http|https):\/\//.test("https://") // ✓ Non-capturing groups

// These don't:
/(\\w+) \\1/.test("hello hello")       // ✗ Backreference
/(?<=@)\\w+/.test("user@domain")       // ✗ Lookbehind (ignored)

Why?

Backtracking requires a call stack and state machine, which is expensive on GPUs. NFAs are compiled to single-pass automata (~10 cycles/char) instead of exponential backtracking.

When It Matters

Rarely in production. Most HTTP workloads use simple patterns:

  • ✅ Validation: email, phone, zip code, URL paths
  • ✅ Extraction: numbers, IDs, quoted strings
  • ❌ Complex nested matching (use a real parser instead)
  • ❌ Recursive patterns (e.g., balanced parentheses — use a parser)

✓ How to Handle It

Option 1: Use Supported Patterns

// Instead of backreference:
const match = /(\\w+)\\s(\\w+)/.exec("hello world");
const isSame = match[1] === match[2];  // Check on CPU after

Option 2: Pre-validate on CPU

// Node.js has full regex support
const isValid = /^(?!.*\\b(\\w+)\\s\\1\\b).*$/.test(str);  // Complex regex on CPU
if (isValid) gpu.process(str);

Option 3: Explicit Parsing Logic

// Instead of recursive regex, write explicit parser:
function parseJson(str) {
  let pos = 0;
  const parseValue = () => {
    if (str[pos] === '{') return parseObject();
    if (str[pos] === '[') return parseArray();
    if (str[pos] === '"') return parseString();
    return parseNumber();
  };
  // ... rest of parser
}

Supported Operations

Feature Status Example
Literals ✅ Full hello, abc
Character classes ✅ Full [a-z], \d, [^abc]
Quantifiers ✅ Full +, *, ?, {n,m}
Alternation ✅ Full (cat|dog)
Anchors ✅ Full ^start, end$
Non-capturing groups ✅ Full (?:...)
Backreferences ❌ No \1, \2
Lookahead/Lookbehind ⚠️ Parsed, no-op (?=...), (?<=...)
Flags ✅ Full i (case-insensitive), g (global)

🚫 No Runtime Code Generation

Impact: Medium Common: Rare

The Constraint

eval() and new Function() do not generate executable code at runtime. They are safe no-ops that return empty values. 

// These compile but don't execute:
const code = "2 + 2";
const result = eval(code);        // ← Returns null
const fn = new Function("return 42");  // ← Returns null

Why?

GPU code is compiled to machine code ahead-of-time by NVIDIA's NVRTC compiler. There is no JIT compiler on the GPU. Generating code at runtime would require shipping a compiler to the GPU, which is impractical.

When It Matters

  • ✅ Static applications (known logic at compile time)
  • ❌ Template engines with computed expressions
  • ❌ Dynamic query builders
  • ❌ Rule engines with user-provided logic

✓ How to Handle It

Option 1: Move Compilation to CPU

// Instead of on GPU:
const expr = "(x * 2) + 1";
const result = eval(expr);  // ✗ GPU can't eval

// Do on CPU:
const template = compile(expr);  // Compile once at startup
const gpu = loadCompiledTemplate(template);
const result = gpu.evaluate(x);  // GPU executes pre-compiled code

Option 2: Use Lookup Tables

// Instead of dynamic rules:
const rules = {
  'RULE_1': (x) => x * 2,
  'RULE_2': (x) => x + 10,
  'RULE_3': (x) => x ** 2
};

// GPU receives rule name + data
const applyRule = (rule, x) => {
  switch(rule) {
    case 'RULE_1': return x * 2;
    case 'RULE_2': return x + 10;
    case 'RULE_3': return x * x;
  }
};

Option 3: Separate Compilation & Execution

// Two-phase model:
// Phase 1 (CPU): Parse and compile user expressions
const userExpr = "amount > 1000 && region == 'US'";
const compiledFn = compile(userExpr);  // CPU-side compilation

// Phase 2 (GPU): Execute pre-compiled logic
const results = gpu.filter({
  data,
  predicate: compiledFn  // Send compiled form to GPU
});

Why This Is Actually Good

Forcing pre-compilation prevents:

  • Code injection attacks
  • Unbounded memory usage (no parsing on GPU)
  • Silent failures (miscompiled expressions)
  • Non-deterministic performance (JIT variations)

📍 Simplified Stack Traces

Impact: Low Common: Only during debugging

The Constraint

Error.stack does not include full unwinding. You get the error message and immediate call site, but not the full chain back to the handler. 

// Full stack (Node.js):
Error: Division by zero
    at compute (server.ts:42:15)
    at transform (server.ts:28:7)
    at handler (server.ts:10:3)

// GPU stack (simplified):
Error: Division by zero
    at compute (kernel:42)

Why?

GPU kernels execute in parallel with no call stack frame preservation. Unwinding requires tracking control flow across 256 parallel threads, which is expensive. Symmetra preserves only the immediate error context.

When It Matters

  • ✅ Error logging (message + location is usually enough)
  • ❌ Deep debugging (need full call chain)

✓ How to Handle It

Option 1: Explicit Error Context

// Add context to errors:
try {
  const result = gpu.compute(data);
} catch (err) {
  throw new Error(
    `Failed during batch processing: ${err.message}`,
    { cause: err }
  );
}

Option 2: Logging at Boundaries

// Log at CPU/GPU boundaries:
const input = prepareData(req.body);
console.log('→ GPU compute:', { input, timestamp: Date.now() });

let result;
try {
  result = gpu.compute(input);
  console.log('← GPU result:', { result });
} catch (err) {
  console.error('GPU error:', {
    error: err.message,
    input,
    timestamp: Date.now()
  });
}

Option 3: Test Critical Paths on CPU

// Unit test with Node.js first (full debugging):
test('compute handles edge cases', () => {
  // Test with full stack traces before deploying to GPU
  expect(() => compute(0)).toThrow();
});

🪞 Limited Metaprogramming

Impact: Low Common: Very rare

The Constraint

Proxy and Reflect are parsed and compile, but have minimal semantics. Property interception doesn't work as expected. 

// This parses but doesn't intercept:
const handler = {
  get: (target, prop) => {
    console.log(`Getting ${prop}`);  // Never prints
    return target[prop];
  }
};

const proxy = new Proxy(data, handler);
console.log(proxy.x);  // Reads directly; handler.get not called

Why?

Full proxy support would require:

  • Runtime trap invocation at property access
  • Type-erased method dispatch
  • Overhead on every property read/write

GPU code prioritizes performance and determinism over reflection.

When It Matters

  • ✅ Reading/writing plain objects
  • ❌ Validation through proxy traps
  • ❌ Observable property changes
  • ❌ Lazy loading of properties

✓ How to Handle It

Option 1: Explicit Validation

// Instead of proxy validator:
function process(data) {
  // Validate upfront on CPU
  if (typeof data.id !== 'number') throw new Error('Invalid id');
  if (typeof data.name !== 'string') throw new Error('Invalid name');

  // Pass validated data to GPU
  return gpu.compute(data);
}

Option 2: Schema-Based Approach

// Define schema once; use for validation:
const schema = {
  id: 'number',
  name: 'string',
  items: 'array'
};

const validate = (obj) => {
  for (const [key, type] of Object.entries(schema)) {
    if (typeof obj[key] !== type) throw new Error(`Invalid ${key}`);
  }
  return true;
};

Option 3: Skip Reflection

// If you need dynamic behavior, implement on CPU:
const result = gpu.process(staticData);  // GPU: static types
const decorated = augmentWithMetadata(result);  // CPU: dynamic

🎯 General Strategy

The most effective approach to working within these constraints is to think of the GPU as a deterministic, data-parallel compute engine rather than a general-purpose runtime.

Do This:

  • CPU handles I/O, variability, and complexity: Request parsing, authentication, data fetching, dynamic logic
  • GPU handles pure computation: Transformation, filtering, aggregation, math on fixed data
  • Pre-allocate and pre-size: All memory and structures decided at request boundary
  • Batch similar work: Send 256 requests at once, not 1 at a time

Don't Do This:

  • Expect GPU to be a drop-in replacement for Node.js
  • Try to use advanced JS features (eval, Proxy, generators) that require runtime support
  • Handle I/O or wait for external events on GPU
  • Make architectural decisions based on missing features; design around the constraint instead
